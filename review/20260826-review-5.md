## 2. 구조적 문제점 (심각도 순)

### 🔴 P1. 헤드가 전체 연산의 43% — 최대 비효율 지점

`models/head.py:9-17`의 `cls_convs`/`reg_convs`가 **128채널 dense 3×3 conv 2개씩**이고, 이것이 80×80 해상도(P3)에 그대로 적용됩니다.

```python
# models/head.py:9-17 — 현재
self.cls_convs = nn.Sequential(
    ConvModule(in_channels, hidden_channels, kernel_size=3, padding=1),   # dense 128→128
    ConvModule(hidden_channels, hidden_channels, kernel_size=3, padding=1)
)
self.reg_convs = nn.Sequential(   # 동일 구조 반복
    ...
)
```

- Neck(`DWSepConv`)에서는 depthwise separable 을 쓰면서 **정작 가장 비싼 헤드는 dense로 둔 일관성 결여**입니다
- 3개 스케일에 가중치를 공유하지만 **연산은 스케일마다 반복** — 공유는 파라미터만 아끼고 MACs 는 아끼지 못합니다

### 🔴 P2. 백본–넥 불균형 — 정확도 상한의 구조적 원인

| | 파라미터 | 연산 |
| :--- | ---: | ---: |
| backbone | 4.78M (85%) | 6.22G (53%) |
| **neck** | **0.23M (4%)** | **0.49G (4%)** |
| head | 0.60M (11%) | 5.05G (43%) |

검출 mAP 는 멀티스케일 융합 품질에 크게 좌우되는데, 현대 검출기(YOLOv8, RT-DETR)는 neck+융합 경로에 전체의 30~40%를 투자합니다. 현재 neck 은 lateral 1×1 conv 3개 + DWSepConv 8개가 전부입니다. **1차 리뷰부터 4회 연속 지적된 "neck 0.3M 미달"(체크리스트 S4)의 본질이 이 불균형입니다.**

### 🔴 P3. xlarge = 분류용 ConvNeXt-XL 사양 그대로 — 검출용 설계가 아님

`models/backbone.py:33`의 `dims [256,512,1024,2048], depths [3,3,27,3]`은 **ImageNet 분류용 ConvNeXt-XL 의 사양과 동일**합니다. 검출 640 입력에 그대로 쓰면:

- stage2 (1024ch × 27블록 @ 40×40) 하나가 **363.5 GMACs = 전체의 61%**
- backbone 347M vs neck 2.0M — 극단적 불균형
- 1×A100 기준 300 에포크에 **~29일** ([TRAINING_PLAN.md](../TRAINING_PLAN.md) §2.3)
- 검출 태스크에서 채널 폭(2048)은 깊이·해상도 대비 mAP 기여가 낮다는 것이 정설입니다

### 🔴 P4. positive 샘플 부족 — 수렴 속도와 소형 객체 정확도 저하

`utils/loss.py`의 `TargetAssigner`가 `in_box AND in_center AND in_level` 고정 규칙이라, GT당 positive 가 **4~12개**에 불과합니다 (3차 리뷰 실측).

| 객체 | positive 수 (실측) |
| :--- | ---: |
| 대형 300×300 | 4 |
| 중형 100×100 | 4 |
| 초소형 12×12 | 1 |

- YOLOX SimOTA 는 dynamic-k 로 GT당 10~30개를 뽑으며, from-scratch 300ep 에서 이 차이가 mAP 수 포인트를 가릅니다
- 초기 손실에서 `obj`(245.3)가 `cls`(11.6)의 21배로 지배적인 현상(TRAINING_PLAN §4.3 R3)도 같은 뿌리입니다 — positive 가 적으니 8,400개 point 대부분이 negative 신호만 받습니다

### 🟠 P5. 그 외 구조 이슈

| # | 위치 | 문제 | 영향 |
| :--- | :--- | :--- | :--- |
| P5-1 | `models/backbone.py:38-41` | 4×4 non-overlapping patchify 스템 | 소형 객체 특징 손실. 검출용은 겹치는 3×3 s2 ×2가 관례 |
| P5-2 | backbone stage0 | stride 4에서 1.01G(8.6%) 소모하나 출력이 neck 으로 직접 가지 않음 | 연산 대비 기여 낮음 |
| P5-3 | `models/neck.py:42-43` | bottom-up 다운샘플이 `max_pool2d` | 학습 불가능한 다운샘플 — 정보 손실 |
| P5-4 | `models/head.py:79` | `exp()` 박스 디코딩 | 무한 범위. `clamp(max=8)`은 응급처치이지 근본 해결이 아님 |
| P5-5 | ROADMAP Phase 2 | RepVGG 재파라미터화 미적용 | 추론 latency 개선 기회 상실 (MACs 불변, 메모리 접근 감소) |
| P5-6 | `utils/loss.py:115` | `DetectionLoss` 가 배치를 파이썬 루프로 순회 | GPU 학습 시 배치 크기에 비례해 느려짐 |

## 3. 속도 개선 방향

### 🔴 S1. 헤드를 depthwise separable 로 — 최소 노력, 최대 효과

`DWSepConv` 는 이미 `models/neck.py:15` 에 있습니다. 4줄 수정입니다.

```python
# models/head.py — DecoupledHead.__init__
from .neck import DWSepConv

self.cls_convs = nn.Sequential(DWSepConv(in_channels), DWSepConv(in_channels))
self.reg_convs = nn.Sequential(DWSepConv(in_channels), DWSepConv(in_channels))
```

**기대 효과** (픽셀당 600,704 → 81,024 MACs):

| 구성 | 헤드 GMACs | nano 총합 | 절감 |
| :--- | ---: | ---: | ---: |
| 현재 (dense 128) | 5.05 | 11.76 | — |
| **DWSep 128** | **0.68** | **7.39** | **-37%** |
| DWSep + hidden 64 | 0.28 | 6.99 | -41% |

- medium 은 헤드 20.0G → 2.7G, **총 59.2 → 41.9G (-29%)**
- 표현력 손실 우려는 §4 A2 의 neck 재투자로 상쇄합니다
- ⚠️ 아키텍처 변경이므로 기존 체크포인트와 비호환 — **학습 전 적용 필수**

### 🔴 S2. xlarge dims 축소

```python
# models/backbone.py:33 — 1줄 수정
'xlarge': {'depths': [3, 3, 27, 3], 'dims': [128, 256, 512, 1024]}   # ConvNeXt-B 폭
```

| | 현재 | 수정 후 (추정) |
| :--- | ---: | ---: |
| backbone GMACs | ~496 | ~124 |
| **총 GMACs** | **594** | **~150** |
| 300 ep @1×A100 | ~29일 | **~7.3일** |

YOLOv8x(129G)급으로 정상화되며, TRAINING_PLAN §3.2 의 "xlarge 300 에포크 불가" 제약이 크게 완화됩니다.

### 🟡 S3. 기타

| 항목 | 방법 | 효과 |
| :--- | :--- | :--- |
| stage0 축소 | 블록 2→1 또는 expansion 4→2 | -0.5G (nano의 4%) |
| RepVGG 재파라미터화 | 학습 시 3×3+1×1+identity → 추론 시 단일 3×3 융합 | MACs 불변, CPU/NPU latency 개선 |
| 헤드 hidden 축소 | 128 → 64 (S1과 병행 가능) | 추가 -0.4G |

## 4. 정확도 개선 방향

### 🔴 A1. SimOTA (또는 TAL) 할당 — 추론 비용 0

`TargetAssigner` 는 1차 리뷰 때부터 교체 가능하게 모듈화되어 있습니다.

- cost = `cls_loss + λ·IoU_loss` 기반 dynamic-k 선택 (YOLOX 방식)
- from-scratch 학습에서 **+2~4 mAP** 가 보고되는 표준 기법
- P4(positive 부족)와 `obj` 손실 지배(TRAINING_PLAN R3)를 **동시에** 해소
- 추론 그래프는 전혀 바뀌지 않음 — NPU/양자화 경로에 무영향

> 도입 시 한 번에 하나씩: 현재 center-prior 로 Stage 2 기준선을 잡은 뒤 SimOTA 를 A/B 하십시오 (2차 리뷰 §7 STEP 1-2 의 원칙과 동일).

### 🟠 A2. S1 절감분을 neck 에 재투자 — 같은 연산량으로 더 높은 mAP

S1 이 절약한 4.4G 중 1~2G만 neck 에 쓰면:

| 방법 | 비용 | 기대 |
| :--- | :--- | :--- |
| BiFPN 블록 2 → 4개 | +0.35G | 융합 반복 증가 |
| DWSepConv → C2f/CSP 스타일 블록 | +0.5~1G | 채널 mixing 강화 |
| `max_pool2d` → stride-2 dwconv (P5-3) | +0.05G | 학습 가능한 다운샘플 |

결과: **총 연산 nano ~9G (현재 -23%)에서 neck 용량은 3~4배** — P2 불균형 해소.

### 🟠 A3. 박스 회귀를 DFL 로 교체

`exp()` 직접 회귀(P5-4) 대신 Distribution Focal Loss — 거리를 16-bin 이산 분포로 예측하고 softmax 가중합으로 복원.

- YOLOv8 채택 방식, **+1~2 mAP**
- `exp` 발산 위험 원천 제거 (`clamp` 불필요)
- softmax·가중합은 헤드 conv 이후이므로 **현재 DeQuantStub 구조와 그대로 호환** (6차 리뷰 §1.2)

### 🟡 A4. 스템을 겹치는 conv 로 (P5-1)

```python
self.stem = nn.Sequential(
    nn.Conv2d(3, dims[0]//2, 3, stride=2, padding=1, bias=False), nn.BatchNorm2d(dims[0]//2), nn.Hardswish(inplace=True),
    nn.Conv2d(dims[0]//2, dims[0], 3, stride=2, padding=1, bias=False), nn.BatchNorm2d(dims[0]),
)
```

비용 +0.1G 수준으로 `map_small` 개선 기대. Conv→BN 순서라 Int8 fuse 도 유지됩니다.

### 🟡 A5. 학습 기법 (TRAINING_PLAN 과 중복 — 요약만)

- Mosaic/MixUp (블로커 B3) · EMA · 증강 종료 구간 — [TRAINING_PLAN.md](../TRAINING_PLAN.md) §3~4
- **지식 증류 (xlarge → nano)**: xlarge 를 학습한다면, nano/medium 학습 시 teacher 로 쓰는 것이 594G(축소 후 150G)를 투자하는 가장 실용적인 명분입니다

## 5. 우선순위 및 실행 시점

| 순위 | 작업 | 노력 | 속도 효과 | 정확도 효과 | 실행 시점 |
| :---: | :--- | :---: | :---: | :---: | :--- |
| 1 | **S1 헤드 DWSep** | 4줄 | **-37% MACs (nano)** | ≈0 (A2 병행 시 +) | **본 학습 전 필수** |
| 2 | **S2 xlarge dims 축소** | 1줄 | **-75% (xlarge)** | 소폭 ↓, 학습 실현성 ↑ | **본 학습 전 필수** |
| 3 | **A1 SimOTA** | 중 | 0 | **+2~4 mAP** | Stage 2에서 A/B |
| 4 | A2 neck 재투자 | 소 | +1~2G | +1~2 mAP | S1과 함께 |
| 5 | A3 DFL | 중 | ≈0 | +1~2 mAP | Stage 2에서 A/B |
| 6 | A4 스템 / S3 stage0 | 소 | 소폭 | `map_small` + | 여유 시 |
| 7 | S3 RepVGG | 중 | latency만 | 0 | 배포 최적화 단계 |

### 실행 원칙

1. **1·2순위는 학습 착수 전에 확정** — 아키텍처가 바뀌면 체크포인트가 비호환이고, 학습 후 변경은 300 에포크 재학습을 의미합니다. TRAINING_PLAN §10 R4("코드와 문서 중 하나는 바뀌어야 한다")의 답이 바로 이 두 항목입니다.
2. **3~5순위는 Stage 2(5k 서브셋, 2시간)에서 A/B** — 한 번에 하나씩 바꿔야 효과 귀속이 가능합니다.
3. 변경 후 **체크리스트 재검증 필수**: grid 8400 · ONNX 비친화 연산 0 · Int8 추론 성공 (§6 스크립트).

import torch, sys

from torch.utils.flop_counter import FlopCounterMode

with FlopCounterMode(display=False) as fc, torch.no_grad():
    m(torch.randn(1, 3, 640, 640))
counts = fc.get_flop_counts()
g = lambda name: sum(v for v in counts.get(name, {}).values()) / 2 / 1e9

total = g('Global')

             'backbone.stages.2', 'backbone.stages.3', 'backbone.downsamples',
             'neck', 'head']:
