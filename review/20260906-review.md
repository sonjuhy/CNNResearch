## 1. 추론 정확도

학습된 모델이 없어 mAP 실측은 불가능합니다. 따라서 **정확도 상한을 결정하는 구조 요인**을 실측 가능한 범위에서 검토했습니다.

### 🔴 1.1 신규 — 레벨 할당 range가 COCO 객체 분포와 불일치

`utils/loss.py:77-80`의 size range는 다음과 같습니다.

```python
lo = torch.where(strides == 8, 0.0,  torch.where(strides == 16, 64.0,  128.0))
hi = torch.where(strides == 8, 64.0, torch.where(strides == 16, 128.0, float('inf')))
```

이 `[0,64] / [64,128] / [128,∞]`는 **FCOS의 5레벨(P3~P7) 임계값 `[0,64,128,256,512,∞]` 중 앞 3개를 그대로 가져온 것**입니다. 3레벨 모델에 적용하면 담당 영역이 심하게 쏠립니다.

| 레벨 | 회귀 반경 | 담당 객체 변(邊) | COCO 인스턴스 비중 (추정) |
| :--- | :--- | :--- | :--- |
| **P3 (stride 8)** | 0 ~ 64 px | **< 128 px** | small 41% + medium 34% + large 일부 ≈ **85%** |
| P4 (stride 16) | 64 ~ 128 px | 128 ~ 256 px | ≈ 10% |
| **P5 (stride 32)** | 128 ~ ∞ px | **> 256 px** | ≈ **5%** |

> COCO 정의: small < 32², medium 32²~96², large > 96². P3 하나가 small·medium 전부와 large 상당수를 담당하고, **P5는 640 이미지에서 256px 이상인 극소수 객체만** 봅니다.

**결과**:
- 멀티스케일 헤드를 만들어 놓고 **사실상 단일 스케일로 학습**됩니다
- medium 객체(32~96px)가 P4의 넓은 문맥을 활용하지 못합니다 — 수용영역 실측: P3 168px vs P4 624px
- P4·P5 헤드 파라미터(공유 conv이지만 BN·scale은 독립)가 거의 학습 신호를 받지 못합니다

**수정** — 3레벨용 재조정 후 Stage 2에서 A/B:

```python
# 후보 A: COCO small/medium/large 경계에 정렬 (객체 변 <64 / 64~128 / >128)
lo = torch.where(strides == 8, 0.0,  torch.where(strides == 16, 32.0, 64.0))
hi = torch.where(strides == 8, 32.0, torch.where(strides == 16, 64.0, float('inf')))
# 후보 B: size range 자체를 제거하고 SimOTA 의 dynamic-k 에 맡김 (7차 A1)
```

### 🔴 1.2 신규 — 평가 좌표계가 공식 COCO와 비호환 (letterbox 부재)

`data/transforms.py`의 `ValTransforms`/`TrainTransforms`가 **종횡비를 무시하고 640×640으로 리사이즈**합니다. 면적 왜곡 실측:

| 원본 해상도 | 640 정사각 리사이즈 후 면적 배율 |
| :--- | ---: |
| 640×480 (COCO 최빈) | **×1.33** |
| 480×640 | ×1.33 |
| 500×375 | **×2.18** |

**세 가지 문제**:
1. **`map_small / medium / large` 오분류** — torchmetrics가 왜곡된 면적으로 등급을 판정하므로 공식 수치와 비교 불가
2. **원본 좌표 역변환 없음** — 예측을 원본 이미지 좌표로 되돌리는 코드가 없어 `pycocotools.COCOeval`(공식 평가)을 쓸 수 없음
3. **학습 효율 손실** — 이미지마다 다른 비율로 객체가 늘어나, 모델이 "종횡비 불변성"을 추가로 학습해야 함

**수정** — letterbox(패딩) 도입 + 변환 정보 보존 + 역변환:

```python
# data/transforms.py — letterbox 예시
def letterbox(image, size=640, pad_value=114/255):
    _, h0, w0 = image.shape
    r = size / max(h0, w0)
    nh, nw = int(round(h0 * r)), int(round(w0 * r))
    image = TF.resize(image, [nh, nw])
    top, left = (size - nh) // 2, (size - nw) // 2
    canvas = torch.full((3, size, size), pad_value)
    canvas[:, top:top+nh, left:left+nw] = image
    return canvas, r, (left, top)           # r·pad 를 targets 에 함께 저장

# 박스: boxes * r + [left, top, left, top]
# 역변환(평가): (pred_boxes - [left, top, left, top]) / r
```

`eval.py`는 역변환 후 **원본 좌표에서 `COCOeval`** 로 평가해야 SOTA 비교가 가능합니다.

## 2. 추론 속도

### 2.1 모듈별 latency vs MACs — 병목이 플랫폼에 따라 뒤집힘

nano, CPU 6 threads, FP32 eager, 640×640:

| 모듈 | GMACs (실측) | MACs 비중 | **latency** | **latency 비중** |
| :--- | ---: | ---: | ---: | ---: |
| backbone | 6.22 | 53% | **134.7 ms** | **68%** |
| neck | 0.49 | 4% | 22.8 ms | 11.5% |
| head | 5.05 | **43%** | 40.3 ms | 20% |
| 합계 | 11.76 | | 198.3 ms | |
| postprocess (최악: 1000박스 NMS) | | | 5.4 ms | |

> 7차 리뷰의 해석적 분해가 `FlopCounterMode` 모듈별 실측과 **정확히 일치**함을 확인했습니다 (head 5.05 / heads.0 3.84 / stage2 2.88 / stage0 1.01 / neck 0.49).

**해석**: CPU에서는 백본의 고해상도 depthwise conv가 **메모리 바운드**라 MACs 이상으로 시간을 먹습니다. 반면 NPU/MACs 관점에서는 헤드가 병목입니다. **최적화 우선순위가 배포 타깃에 따라 다릅니다.**

### 2.2 구조 개선안 실측 (nano)

| 변형 | GMACs | CPU 6T | CPU 1T |
| :--- | ---: | ---: | ---: |
| 현재 (dense head 128) | 11.76 | 193.1 ms | 486.4 ms |
| **S1: 헤드 DWSep** | **7.39 (-37%)** | 179.6 (-7%) | **361.7 (-26%)** |
| S1 + 백본 dw 5→3 | 7.30 | 176.9 | 357.8 |
| **S1 + dw3 + stage0 블록 2→1** | 6.81 (-42%) | **148.8 (-23%)** | — |

| 발견 | 의미 |
| :--- | :--- |
| S1은 MACs -37%지만 6T CPU에선 -7% | 멀티스레드가 dense conv를 잘 병렬화. **1스레드(엣지)에선 -26%로 효과가 드러남.** NPU에선 MACs가 그대로 반영 |
| **stage0 블록 1개 제거 = latency -16%p** (MACs는 -4%) | 160×160 해상도의 depthwise가 메모리 바운드. **CPU 타깃이면 S1보다 우선** |
| dw 5→3은 효과 없음 | depthwise MACs는 원래 작음. kernel 축소는 무의미 |

### 2.3 런타임 경로별 실측

| 경로 | latency | 대비 eager |
| :--- | ---: | ---: |
| PyTorch eager FP32 | 198.3 ms | 1.00× |
| **ONNX Runtime FP32** | **132.1 ms** | **1.50×** |
| **Int8 fbgemm (x86)** | **67.3 ms** | **2.95×** |
| Int8 qnnpack (x86) | 267.0 ms | 0.74× — ARM 전용 백엔드라 x86 수치는 무의미 |

### 2.4 종합 전망

| 시나리오 | 예상 latency | FPS |
| :--- | ---: | ---: |
| 현재 eager | 198 ms | 5 |
| 구조 개선(S1+stage0) + ORT | ~100 ms | 10 |
| **구조 개선 + Int8** | **~50 ms** | **~20** |
| 1스레드 엣지, 구조 개선 후 | ~360 ms | 3 |

6스레드 CPU에서 20 FPS는 도달 가능하나, **1스레드 엣지에서 "실시간"은 백본 채널 축소 없이는 불가능**합니다. `MODEL_ARCHITECTURE.md`의 nano 티어 정의(라즈베리파이·스마트폰 NPU 실시간) 재검토가 필요합니다 (TRAINING_PLAN R4).

### 🔴 3.2 신규 — 학습 역학 실측: `obj` 손실 지배가 학습 중 심화

현행 레시피 그대로(lr 1e-3, warmup 없음, wd 1e-4, batch 4, GT 12개) 20 step 실측:

```
step   total     cls     box      obj   obj/(cls+box)  grad_norm  num_pos
   0  224.95  11.403   4.611   208.93       13.0        319.9      108
   3  204.00   4.536   4.115   195.35       22.6        305.6      108
  10  150.41   0.114   1.897   148.39       73.8        225.3      108
  19  117.28   0.015   1.479   115.79       77.5        196.6      108
```

| 관찰 | 해석 |
| :--- | :--- |
| `grad_norm` 200~350, clip 10이 **매 스텝 20~35배**로 발동 | AdamW는 파라미터별 정규화를 하므로 균일 클리핑은 업데이트 크기를 거의 바꾸지 않습니다. 클리핑이 "보호"하는 것이 아니라 **그래디언트 방향 자체가 obj에 지배**되는 것이 실제 문제 |
| `obj/(cls+box)`가 13 → 78로 **악화** | cls가 먼저 수렴하면 이후 학습은 사실상 objectness 이진 분류만 최적화 |
| `num_pos` 108 / 33,600 point = **0.3%** | GT당 9개. 8,400 point의 99.7%가 negative 신호만 생성 |

**대응** (Stage 2에서 A/B):
1. **SimOTA** 도입 → positive 10~30개/GT (7차 A1). 근본 해법
2. `obj` 가중치 0.5로 하향 → 임시 완화
3. cls 손실을 negative에도 확장하거나 **VarifocalLoss**(cls·obj 통합 품질 점수)로 교체 → obj 브랜치의 지배 구조 자체를 제거

### 3.3 그 외 레시피 관찰

| 항목 | 내용 |
| :--- | :--- |
| `DetectionLoss` 배치 루프 | `utils/loss.py:115`가 파이썬 `for b in range(B)` — 배치 64에서 GPU 유휴 발생. 벡터화 필요 |
| FocalLoss on positives only | negative 클래스 판별이 `obj`에만 의존. YOLOX 방식이지만 §3.2와 결합해 취약 |

| 손실 가중치 `box × 5.0` | YOLOX 관행값. Stage 2에서 3/5/7.5 스윕 |

### 4.2 조치 우선순위

| 순위 | 조치 | 위치 | 규모 | 효과 |
| :---: | :--- | :--- | :--- | :--- |
| 🔴 1 | **`export.py` 체크포인트 로드** | `export.py:13` | 4줄 | 배포 산출물 정상화 |
| 🔴 2 | **레벨 range 3레벨용 재조정** | `utils/loss.py:77-80` | 2줄 | P4·P5 활성화, medium 객체 문맥 확보 |
| 🔴 3 | **letterbox + 역변환 + COCOeval** | `data/transforms.py`, `eval.py` | 중 | 공식 mAP 비교 가능 |
| 🟠 4 | SimOTA (또는 obj 가중치 하향) | `utils/loss.py` | 중 | obj 지배 해소, +2~4 mAP |
| 🟠 5 | 구조: stage0 축소 (CPU) / 헤드 DWSep (NPU) | `models/` | 소 | latency -23% / MACs -37% |
| 🟠 6 | `train.py` 레시피 12항목 | `train.py` | 중 | TRAINING_PLAN Stage 0 |
| 🟡 7 | `DetectionLoss` 배치 벡터화 | `utils/loss.py:115` | 소 | GPU 학습 속도 |

**1~3번은 학습 착수 전 필수**입니다. 특히 2번은 1줄짜리 수정인데, 방치하면 300 에포크 학습이 단일 스케일 검출기를 만듭니다.

### 4.3 총평

7차까지 "동작하는가"를 검증했다면, 이번 8차는 **"제대로 동작하는가"** 를 본 첫 리뷰입니다.

그 결과, 코드가 돌아가는 것과 별개로 **설계 의도가 실제로 구현됐는지**에서 세 가지 균열이 발견됐습니다 — 멀티스케일 헤드가 단일 스케일로 동작하는 레벨 range, 공식 벤치마크와 비교할 수 없는 평가 좌표계, 그리고 학습되지 않은 가중치를 내보내는 export. 세 가지 모두 **mAP 숫자가 나오기 전에는 드러나지 않는 종류**의 문제이며, 실제 COCO 데이터가 확보되면 가장 먼저 부딪힐 벽입니다.

속도 측면의 핵심 교훈은 **MACs와 latency가 다르다**는 것입니다. 7차에서 MACs 기준으로 헤드를 1순위로 꼽았지만, CPU 실측에서는 stage0 블록 하나가 더 큰 병목이었습니다. 배포 타깃(CPU vs NPU)을 먼저 확정해야 최적화 순서가 정해집니다.

### 5-2. 모듈별 latency (§2.1)

```python
import torch, sys, time
sys.path.insert(0, '.')
from models.detector import SOTADetector
torch.set_num_threads(6)
m = SOTADetector(scale='nano').eval(); x = torch.randn(1, 3, 640, 640)
tm = {}
def hook(name):
    def pre(mod, inp): tm[name + '_s'] = time.perf_counter()
    def post(mod, inp, out): tm[name] = tm.get(name, 0) + time.perf_counter() - tm[name + '_s']
    return pre, post
for n, mod in [('backbone', m.backbone), ('neck', m.neck), ('head', m.head)]:
    pre, post = hook(n); mod.register_forward_pre_hook(pre); mod.register_forward_hook(post)
with torch.no_grad():
    for _ in range(3): m(x)
    tm.clear(); N = 10; t = time.perf_counter()
    for _ in range(N): m(x)
    total = (time.perf_counter() - t) / N * 1000
for n in ['backbone', 'neck', 'head']:
    print(f"{n:10s} {tm[n]/N*1000:7.1f} ms ({tm[n]/N*1000/total*100:5.1f}%)")
```

### 5-5. 학습 역학 (§3.2)

```python
import torch, sys
sys.path.insert(0, '.')
from models.detector import SOTADetector
from utils.loss import DetectionLoss
torch.manual_seed(0)
m = SOTADetector(scale='nano'); crit = DetectionLoss()

x = torch.rand(4, 3, 640, 640)
tg = [{'boxes': torch.tensor([[100., 100., 300., 300.], [350., 350., 500., 480.], [20., 20., 60., 60.]]),
       'labels': torch.tensor([3, 7, 11])} for _ in range(4)]

for i in range(20):
    pred = m(x); ld = crit(pred, tg)
    opt.zero_grad(); ld['loss_total'].backward()

    if i in (0, 3, 10, 19):
        c, b, o = ld['loss_cls'].item(), ld['loss_box'].item(), ld['loss_obj'].item()
        print(f"step {i:2d} cls={c:6.3f} box={b:6.3f} obj={o:7.2f} obj/(c+b)={o/(c+b):5.1f} grad={gn:6.1f} pos={npos}")
```
